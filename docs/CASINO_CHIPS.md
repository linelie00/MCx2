# CASINO CHIPS — 칩 영구 저장 계획

블랙잭 칩을 판마다 초기화하는 지금 방식에서 **영구 저장**으로 옮기는 계획.
아직 만들지 않았다. 만들 때 이 문서대로 하면 된다. (작성: 2026-09-09)

> 관련 문서: 서버 구조와 배포는 [DEPLOY.md](DEPLOY.md), 기능 흐름은 [FEATURES.md](FEATURES.md).

---

## 1. 지금 상태

이음매는 이미 만들어 뒀다. [`bot/src/casino/wallet.js`](../bot/src/casino/wallet.js) 의
두 함수가 지금은 상수와 no-op 이다.

```js
export async function load(guildId, userIds)   // 지금: 전원 START_CHIPS
export async function commit(guildId, deltas)  // 지금: 아무것도 안 함
```

이렇게 만들어 둔 이유가 셋이고, 셋 다 이번 작업에서 값을 한다.

- **처음부터 async 다.** 부르는 쪽이 이미 `await` 하고 있어서 호출부를 안 고쳐도 된다.
- **잔액이 아니라 증감(delta)을 넘긴다.** 서버 JSON 스토어는 락이 없어서 delta 적용만 안전하다.
- **호출부가 두 곳뿐이다.** 판 시작(`load`)과 정산(`commit`). 둘 다 인터랙션 응답 경로 밖이라
  느린 HTTP 를 넣어도 3초 시한과 무관하다.

그래서 **봇에서 바뀌는 것은 `wallet.js` 두 함수와 `api.js` 요청 함수뿐이다.**
`state.js`·`render.js`·대사·버튼은 손대지 않는다.

## 2. 확정된 결정

| 항목 | 결정 |
|---|---|
| 저장 위치 | 서버(`DATA_DIR` 볼륨). 봇 서비스에는 볼륨이 없다 |
| 키 | **디스코드 `userId` 하나.** 길드로 나누지 않는다 |
| NPC 칩 | **저장하지 않는다.** 미겔·마티암은 매 판 새로 받는다 |
| 파산 복구 | **`/출첵`** — 하루 한 번 칩을 받는다 |
| 주고받기 | **`/칩 양도`** — 사람끼리 칩을 넘긴다 |
| 저장 실패 | 판에 **"저장 안 됨"** 한 줄을 띄운다. 판은 계속 돈다 |

### NPC 를 저장하지 않는 이유

자리 id 가 사람은 디스코드 id, NPC 는 `npc:migel` 꼴이다([state.js](../bot/src/blackjack/state.js)).
NPC 도 같이 저장하면 **미겔이 영구 파산**해서 판에 못 앉는 날이 온다. NPC 가 못 앉는
블랙잭은 재미가 없다. 그래서 `load`·`commit` 양쪽에서 `npc:` 로 시작하는 id 를 거른다 —
서버는 NPC 를 아예 모른다.

## 3. 데이터

`$DATA_DIR/chips.json` (로컬은 `server/src/data/chips.json`).

```json
{
  "balances": {
    "123456789012345678": { "chips": 1250, "claimedAt": "2026-09-09", "updatedAt": "2026-09-09T12:31:04.221Z" }
  }
}
```

- 키는 디스코드 유저 id 문자열. **없는 사람은 `START_CHIPS`(1000)로 친다** — 첫 참가에
  별도 등록 절차가 없다.
- `claimedAt` 은 `/출첵` 판정용 **KST 날짜**(`YYYY-MM-DD`). 서버 시간대와 무관하게
  한국 날짜로 하루를 나눈다. 봇의 [`pickOfDay.js`](../bot/src/pickOfDay.js) `dayKey()` 와 같은 방식
  (`Intl.DateTimeFormat('sv-SE', { timeZone: 'Asia/Seoul' })`)을 서버에도 똑같이 쓴다.
- 시드 `chips.seed.json` 은 `{ "balances": {} }`. **`server/.gitignore` 에
  `/src/data/chips.json` 을 추가**해야 한다(다른 라이브 파일도 전부 명시돼 있다).

## 4. 서버에 추가할 것

기존 리소스 한 벌과 같은 모양이다. `routes/` + `controllers/` + `services/` + `data/`.

| 파일 | 내용 |
|---|---|
| `services/chipsStore.js` | `movieStore.js` 를 그대로 본뜬다. `FILE`/`SEED` 경로와 폴백 모양만 다르다 |
| `controllers/chipsController.js` | 조회 · delta 적용 · 출첵 · 양도 |
| `routes/chips.js` | 아래 엔드포인트 |
| `middleware/requireBot.js` | `X-Bot-Key` |
| `data/chips.seed.json` | `{ "balances": {} }` |
| `app.js` | `require` 한 줄 + `app.use('/api/chips', chipsRoutes)` 한 줄 |

### 엔드포인트

| 메서드 | 경로 | 용도 |
|---|---|---|
| `GET` | `/api/chips?ids=a,b,c` | 잔액 조회. 없는 id 는 `START_CHIPS` |
| `POST` | `/api/chips/deltas` | `{ deltas: { id: ±n } }` 적용, 새 잔액 반환 |
| `POST` | `/api/chips/claim` | `{ userId }` 출첵. 오늘 이미 받았으면 **409** |
| `POST` | `/api/chips/transfer` | `{ from, to, amount }` 양도 |

전부 쓰기는 `requireBot`. 조회도 봇만 쓰면 되니 굳이 공개할 이유가 없다.

### 인증을 `requireOwner` 로 하지 않는 이유

`requireOwner` 도 **쓸 수는 있다** — 유저 id 를 본문에 싣고 오너 키는 쓰기 권한으로만
쓰면 된다. 그래도 봇 전용 키를 따로 두는 편이 낫다.

오너 패스코드는 **사이트에서 사람이 직접 입력하는 값**이다. 칩 엔드포인트가 그걸 받으면
브라우저에서도 아무 사람의 잔액을 조작할 수 있게 된다. 칩은 봇만 쓰므로 키도 봇만 갖는 게 맞다.
덤으로 `req.owner` 가 "봇인데 사백인 척" 하는 거짓말이 되지 않는다.

부팅 때 봇이 키를 한 번 확인하게 해 두면(`checkOwnerKeys()` 가 `/api/auth/me` 를 찌르는 것과
같은 방식) 잘못된 키가 첫 판이 아니라 **배포 로그**에서 드러난다.

## 6. 반드시 지킬 것

여기 적힌 다섯은 안 지키면 **칩이 복제되거나 사라진다.** 순서대로 중요하다.

### 6-1. `deltas()` 는 누적값이다 — 커밋에 성공하면 기준점을 옮겨야 한다

지금 [`settleAndShow`](../bot/src/commands/blackjack.js) 는 **핸드마다** `commit(game.chips.deltas())` 를 부른다.
그런데 `deltas()` 는 **판을 시작한 시점 대비 누적**이다.

```
1핸드 정산  deltas = +100   서버에 +100 → 1100
2핸드 정산  deltas = +250   서버에 +250 → 1350   ← 틀렸다. 1250이어야 한다
```

서버가 delta 를 더하는 방식인 이상 이건 반드시 터진다. **커밋에 성공하면 `ledger` 의
기준점(`start`)을 현재 잔액으로 옮긴다.** 그러면 다음 `deltas()` 는 직전 커밋 이후분만 담는다.

```js
// wallet.js — ledger 에 추가
rebase() { Object.assign(start, chips); }
```

그리고 이 설계에는 공짜로 따라오는 이득이 있다. **커밋이 실패하면 리베이스를 안 하므로,
다음 핸드 커밋이 성공할 때 밀린 몫까지 함께 반영된다.** 서버가 잠깐 죽었다 살아나면
저절로 만회된다.

### 6-2. `load` 가 실패하면 판을 시작하지 않는다

잔액을 못 읽었는데 `START_CHIPS` 로 진행하면 **칩이 복제된다.** 실제 잔액이 200인 사람이
1000으로 놀고, 나중에 커밋이 성공하면 그 차액이 그대로 서버에 얹힌다.

그래서 `load` 실패는 **시작 거절**이다. 대기실에서 `deny()` 로 사유를 보여주고 판을 안 연다.
(반대로 `commit` 실패는 안전하다 — 칩은 인메모리 장부에서만 깎였으므로 그 핸드가
없던 일이 될 뿐이고, 6-1 덕에 다음에 만회된다.)

### 6-3. 스토어의 read 와 write 사이에 `await` 을 넣지 않는다

스토어에 락은 없지만 노드가 단일 스레드라, `read()` → 수정 → `write()` 를 **한 동기 블록**으로
하면 다른 요청이 끼어들 수 없다. `commit` 이 잔액이 아니라 delta 를 넘기게 만들어 둔 것이
바로 이걸 성립시키기 위해서다.

이미 어긴 선례가 있다 — `playlistController.addTrack` 이 `read()` → `await youtube.fetch…` →
`write()` 를 해서, 동시에 두 개를 추가하면 하나가 유실된다. 칩에서는 절대 그러면 안 된다.

### 6-4. 칩만은 임시 파일에 쓰고 `rename` 한다

스토어의 `read()` 는 파싱에 실패하면 **에러가 아니라 빈 컬렉션을 돌려준다.** 쓰다가
프로세스가 죽어 파일이 반쪽 나면 다음 조회에서 조용히 "전원 잔액 0" 으로 읽히고,
그 상태로 한 번 더 쓰면 끝이다.

영화·플리는 시드가 받쳐 주지만 **칩은 유일본이다.** `chips.json.tmp` 에 쓰고 `fs.renameSync`
하는 것으로 충분하다(같은 파일시스템 안의 rename 은 원자적이다).

### 6-5. `express.json()` 은 라우트마다 붙인다

이 서버에는 **전역 `express.json()` 이 없다.** 라우트 체인에 직접 넣는다.

```js
router.post('/deltas', requireBot, express.json(), ctrl.applyDeltas);
```

빠뜨리면 `req.body` 가 비어서 **에러 없이 잔액이 안 바뀐다.**

## 7. 새 명령 둘

### `/출첵`

하루 한 번 칩을 받는다. **판정은 서버가 한다** — 봇이 재시작해도 잊지 않아야 하고,
`claimedAt` 이 잔액과 같은 파일에 있어야 한 번의 쓰기로 끝난다.

- 지급액 **500칩 고정**. 최소 베팅(50)으로 열 판은 되는 양이고, 파산해도 하루 지나면 돌아온다.
  (잔액에 따라 더 주는 보정도 생각해 봤지만, 규칙이 단순한 편이 낫다. 조절할 곳은 상수 하나다.)
- 이미 받았으면 409 와 함께 **언제 다시 받을 수 있는지**를 알려 준다. "내일 오세요" 보다
  "오늘 몫은 이미 받으셨어요 (다음 00시)" 가 낫다.
- 칩은 카지노 공용 모듈에 있으므로, 나중에 카지노 게임이 하나 더 생겨도 `/출첵` 은 그대로 쓴다.

### `/칩`

- `/칩 잔액` — 자기 잔액. **양도보다 먼저 필요하다.** 얼마 있는지 모르면 못 보낸다.
- `/칩 양도 [상대] [액수]` — 사람끼리만. NPC 는 저장을 안 하므로 대상이 될 수 없다.

양도에서 막아야 할 것들.

- 자기 자신에게 보내기
- 0 이하, 정수가 아닌 값, **50의 배수가 아닌 값** (지갑에 소수가 들어오면 안 된다)
- 잔액 초과
- **진행 중인 판에 앉아 있는 동안** ← 놓치기 쉬운 함정이다

마지막 것을 안 막으면 인메모리 장부와 서버 잔액이 어긋난다. 판이 도는 동안 칩은
`ledger` 안에만 있고 서버는 판 시작 시점 잔액을 들고 있으므로, 그 사이에 서버 잔액을
건드리면 정산 때 delta 가 얹히면서 **없던 칩이 생기거나 사라진다.**
`state.forChannel` 로 진행 중인 판을 찾아 거절하면 된다.

## 8. "저장 안 됨" 표시

`commit` 이 던지는 대신 성공 여부를 돌려주고, 실패하면 판에 표시한다.

```
딜러: npc · Blackjack 3:2 · Dealer stands on 17 · ⚠ 칩 저장 안 됨
```

푸터 한 줄이면 충분하다. 판은 계속 돌아야 한다 — 대사가 그렇듯 저장도 있으면 좋은
것이지 판을 막을 이유가 아니다. 다음 커밋이 성공하면(6-1) 표시를 지운다.

## 9. 커밋 순서

1. `[Feat]: 칩 저장소 — 서버` — 스토어·컨트롤러·라우트·`requireBot`. 봇은 아직 안 부른다
2. `[Feat]: 칩을 서버에 저장` — `wallet.js` 의 `load`/`commit` + `ledger.rebase` + `api.js`
3. `[Feat]: /출첵` — 하루 한 번 지급
4. `[Feat]: /칩` — 잔액·양도
5. `[Feat]: 저장 실패를 판에 표시`

1번까지는 봇 동작이 안 바뀌고, 2번부터 각 단계에서 계속 플레이 가능하다.
2번 뒤에 `cd bot && npm run register` 는 필요 없고, 3·4번 뒤에는 필요하다.

## 10. 검증

**서버 단독**

- 없는 id 조회 → `START_CHIPS`
- 같은 delta 를 두 번 보내면 두 번 적용되는지(멱등이 아님을 확인 — 그래서 6-1 이 필요하다)
- 출첵 두 번 → 두 번째 409
- 양도: 잔액 초과 / 자기 자신 / 50 배수 아님 → 전부 400
- `chips.json` 을 손으로 반쪽 내고 조회 → **0 이 아니라 오류**가 나야 한다(6-4 확인)

**봇까지**

- 한 판에서 여러 핸드를 두고 서버 잔액이 **판 종료 시점 잔액과 정확히 일치**하는지 ← 6-1 의 회귀 테스트
- 서버를 내린 채 판 시작 → 시작 거절
- 판 도중에 서버를 내렸다가 올리기 → "저장 안 됨" 이 떴다가 다음 정산에서 사라지고,
  밀린 몫이 한 번에 반영되는지
- 판에 앉은 채 `/칩 양도` → 거절
- 미겔·마티암이 파산할 때까지 여러 판 → 다음 판에 다시 1000으로 앉는지(NPC 는 저장 안 함)

**칩 총합 보존**은 지금도 `scripts/simulate-blackjack.mjs` 가 판 안에서 검사한다.
저장이 붙으면 그 검사가 **판 밖으로 확장**된다 — 판 시작 잔액 합 + 그 판의 순증감 =
판 종료 잔액 합. 이걸 헤드리스로 한 번 돌려 두면 6-1 을 놓칠 수 없다.
